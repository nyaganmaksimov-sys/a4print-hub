# Production Farm — Phase 19: страхование и улучшения оборудования

## Цель

Phase 19 закрывает два оставшихся риска производственной фермы: потерю контроля над страховым покрытием оборудования и отсутствие отдельного реестра вложений, которые не являются обычным ремонтом.

Существующий реестр `equipment_assets` остаётся каноническим. Новый этап не создаёт второй справочник оборудования и не смешивает модернизации с журналом ТО.

## Страховые полисы

Добавлена таблица `equipment_insurance_policies`.

Она хранит:

- оборудование;
- страховую компанию;
- номер полиса;
- страховую сумму;
- стоимость страховой премии;
- начало и окончание действия;
- статус `DRAFT / ACTIVE / EXPIRED / CANCELLED / CLAIM`;
- ссылку на существующий `documents`;
- примечание и аудит создания/изменения.

Один и тот же номер полиса не может быть повторно создан для одного станка.

## Улучшения и модернизации

Добавлена таблица `equipment_improvements`.

Типы:

- `UPGRADE` — модернизация;
- `REPAIR_UPGRADE` — ремонт, одновременно улучшивший характеристики;
- `SAFETY` — улучшение безопасности;
- `SOFTWARE` — ПО/прошивка/лицензия;
- `ACCESSORY` — оснастка или дополнительный модуль;
- `OTHER` — другое улучшение.

Для записи фиксируются стоимость, оценка прироста стоимости оборудования и ожидаемое продление ресурса в месяцах. Это управленческие показатели; они не переписывают автоматически бухгалтерскую стоимость оборудования.

## Read model

`equipment_risk_overview` — `SECURITY INVOKER` view, которая для каждого станка показывает:

- число активных полисов;
- дату окончания текущего покрытия;
- страховую сумму и премию;
- полисы, заканчивающиеся в ближайшие 30 дней;
- активные полисы с уже прошедшей датой;
- количество улучшений;
- накопленную стоимость улучшений;
- оценочный прирост стоимости;
- суммарное продление ресурса;
- состояние `INSURED / POLICY_EXPIRING / POLICY_EXPIRED / NO_ACTIVE_POLICY`.

`anon` доступа к этой витрине не имеет.

## Интерфейс

В `admin/equipment.html` подключён модуль `equipment-risk-assets.js` и стили `equipment-risk-assets.css`.

В блоке **«Страхование и улучшения»** сотрудник видит:

- сколько станков застраховано;
- сколько полисов истекает в течение 30 дней;
- сколько активных полисов уже просрочено;
- сколько денег зафиксировано как вложения в модернизации;
- список полисов и их состояние;
- историю улучшений по станкам.

С правом `equipment.manage` можно создавать и редактировать полисы и улучшения. С `equipment.view` доступен только просмотр.

## Автоматический контроль срока

Добавлена append-only таблица `equipment_insurance_notice_events` с уникальностью:

`policy_id + valid_until + notice_kind`.

Типы уведомлений:

- `DUE_30`;
- `DUE_7`;
- `EXPIRED`.

Функция `emit_equipment_insurance_notifications()` создаёт уведомления активным администраторам и сотрудникам с `equipment.manage`. Повторный запуск не создаёт дубль одного и того же события.

Функция `expire_equipment_insurance_policies()` переводит `ACTIVE` → `EXPIRED`, если дата уже прошла.

При доступном `pg_cron` создаётся задача:

`equipment-insurance-daily` → `15 6 * * *`.

Сначала она закрывает просроченные полисы, затем отправляет новые уведомления.

Обе фоновые функции закрыты для `anon` и `authenticated`; выполнять их может только серверный `service_role`/cron.

## Безопасность

- RLS включён на полисах и улучшениях;
- чтение требует `equipment.view`;
- изменение требует `equipment.manage`;
- уведомительный журнал не доступен браузеру на запись;
- SECURITY DEFINER фоновые функции используют `search_path=''`;
- документы не дублируются: полис/улучшение может ссылаться на существующий `documents.id`;
- `equipment_risk_overview` работает как `security_invoker`.

## Проверка рабочей Supabase

Миграция применена в рабочий проект `A4PRINT HUB`.

После применения проверяются:

1. создание временного полиса на существующее оборудование;
2. появление состояния `POLICY_EXPIRING`/`POLICY_EXPIRED` в зависимости от даты;
3. дедупликация уведомления при повторном запуске фоновой функции;
4. создание улучшения с затратами, приростом стоимости и продлением ресурса;
5. корректные агрегаты в `equipment_risk_overview`;
6. полный `ROLLBACK`, чтобы тестовые данные не оставались в production.
