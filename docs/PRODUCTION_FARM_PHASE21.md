# Production Farm Phase 21 — допсоглашения и продление договоров

Phase 21 запрещает тихое изменение юридически значимых условий уже действующего договора оборудования. Для `ACTIVE`/`SUSPENDED` договора срок, доли, порядок расчёта, аренда/выкуп, ответственность за ремонт и срок уведомления меняются через отдельное аудируемое дополнительное соглашение.

## Жизненный цикл

1. `DRAFT` — сотрудник HUB формирует изменения и дату вступления.
2. `APPROVED` — HUB утверждает ДС. Одновременно центральный документ получает статус `APPROVED`.
3. `SIGNED` — факт подписания фиксируется на документе. Само ДС остаётся `APPROVED`, пока условия ещё не применены.
4. `APPLIED` — после наступления `effective_on` подписанное ДС атомарно меняет только согласованные поля договора, а документ становится `ACTIVE`.

Черновик или ещё не подписанное утверждённое ДС можно отменить с обязательной причиной. Подписанное ДС простым действием `Отменить` отменять нельзя: для юридически значимого изменения требуется новое действие/соглашение.

## Какие условия можно менять

Через ДС разрешены `ends_on`, доли HUB/владельца, расчётная база, политика прямых затрат, периодичность и день расчёта, ответственность за ремонт, срок уведомления о расторжении, арендный платёж, параметры выкупа и JSON `terms`.

`settlement_day` ограничен диапазоном 1–28, как и в основной таблице договоров. Для `REVENUE_SHARE` доли должны давать 100%. Перечислимые значения проверяются ещё при создании ДС, а не только при применении.

Смена состава оборудования не маскируется под ДС: старый редактор активного договора возвращает `ACTIVE_CONTRACT_EQUIPMENT_CHANGE_REQUIRES_NEW_ANNEX`. Для юридических условий действует `ACTIVE_CONTRACT_REQUIRES_AMENDMENT`.

## Документы и снимки состояния

В центральном архиве `documents` зарегистрирован тип `EQ_CONTRACT_AMENDMENT` с обязательной подписью. Для каждого ДС сохраняются:

- `before_snapshot` — юридические условия до изменения;
- `proposed_changes` — только согласованные изменения;
- `after_snapshot` — состояние после успешного применения;
- связь с договором, партнёром и самим ДС через `document_links`.

При утверждении и применении сервер сверяет исходный snapshot. Если договор успел измениться другим законным процессом, операция останавливается с `CONTRACT_CHANGED_SINCE_DRAFT` вместо применения устаревшего ДС.

## Доступ

HUB работает через `list_equipment_contract_amendments()` и управляющие RPC. Все управляющие действия требуют `equipment.contracts.manage`.

Партнёр использует read-only `get_my_equipment_contract_amendments()` и `get_equipment_contract_amendment_document()`. `current_partner_id()` ограничивает выборку собственным партнёром. Черновики партнёру не публикуются.

SECURITY DEFINER функции Phase 21 используют пустой `search_path`. Внутренние helper/trigger functions не имеют EXECUTE для browser roles; публичные RPC доступны `authenticated` и выполняют внутреннюю авторизацию.

## Интерфейс

HUB: `admin/equipment-contract-amendments.html` — очередь ДС, KPI, фильтры, создание, утверждение, фиксация подписи, применение, отмена и просмотр документа.

Партнёр: вкладка `Допсоглашения` в `partner/equipment.html` — только чтение, статус, дата вступления, основание, изменяемые условия и просмотр `Было → Станет`.

## Проверка на рабочей Supabase

Полный сценарий выполнялся в транзакции с `ROLLBACK` и завершился результатом:

`phase21_contract_amendments_ok`

Проверено:

- прямое изменение активного договора заблокировано;
- ДС создаётся с snapshot исходных условий;
- неподписанное ДС нельзя применить;
- после фиксации подписи и даты вступления изменяются только утверждённые поля;
- сохраняется состояние после применения;
- второй партнёр не видит чужое ДС;
- тестовые записи после `ROLLBACK` отсутствуют.
