# Производственная ферма — этап 2

Этап 2 подключает **реальное оборудование** к существующим `production_jobs` и считает фактическое машинное время по запускам и паузам.

## Что изменено

### `production_jobs`

Существующая таблица заданий расширена, а не заменена. Добавлены:

- `order_item_id` — конкретная позиция заказа;
- `equipment_id` — конкретное оборудование;
- `operation_type` — тип производственной операции;
- `quantity`;
- `planned_machine_minutes`;
- `actual_machine_minutes` — накопленное закрытое машинное время;
- `operation_amount` — сумма операции для следующих этапов финансового распределения;
- `primary_material_id` — основной материал из существующего каталога;
- `production_cost` — поле производственной себестоимости для последующего расчёта материалов и энергии.

Типы операций на этапе 2:

- 2D-печать;
- FDM 3D-печать;
- фотополимерная 3D-печать;
- лазерная резка;
- лазерная гравировка;
- ЧПУ;
- ламинация;
- постпечатная обработка;
- сборка;
- другое.

## Машинные сессии

Добавлена `production_job_runs`.

Каждый реальный запуск создаёт отдельный сегмент:

1. `START` / `RESUME` — открывается сегмент;
2. `PAUSE` — сегмент закрывается с причиной `PAUSED`;
3. `COMPLETE` — сегмент закрывается с причиной `DONE`;
4. `CANCEL` — сегмент закрывается с причиной `CANCELLED`;
5. смена оборудования во время работы закрывает текущий сегмент как `EQUIPMENT_CHANGED`.

Для одного задания и одной машины может существовать только один открытый сегмент. На одном физическом оборудовании одновременно может выполняться только одно задание.

Машинное время считается по `clock_timestamp()`, а не `now()`: `now()` в PostgreSQL фиксирован на начало транзакции и непригоден для измерения продолжительности операции внутри одной транзакции.

## Автоматический статус оборудования

`equipment_assets.operational_status` синхронизируется с производством:

- активное задание → `WORKING`;
- есть очередь / пауза → `QUEUED`;
- заданий нет → `FREE`.

Состояния `MAINTENANCE`, `REPAIR`, `FAULT`, `WAITING_PARTS`, `OFFLINE`, `RETIRED` система не снимает автоматически. Запуск задания на таком оборудовании блокируется.

Списанное оборудование автоматически считается `RETIRED`.

## Совместимость со старым интерфейсом

Старый статусный select в `production-modern.js` **не удалён**. Триггер `sync_production_job_execution()` работает на уровне БД, поэтому даже прямое изменение статуса существующим интерфейсом корректно открывает/закрывает машинные сессии, если у задания назначено оборудование.

Существующая синхронизация `ORDER ↔ PRODUCTION JOB` остаётся без замены.

## RPC

### `configure_production_job(...)`

Настраивает на существующем задании:

- оборудование;
- позицию заказа;
- операцию;
- количество;
- плановое время;
- сумму операции;
- основной материал;
- плановую себестоимость.

### `transition_production_job(job_id, action)`

Поддерживает:

- `START`;
- `RESUME`;
- `PAUSE`;
- `COMPLETE`;
- `CANCEL`.

Обе функции требуют `production.manage`.

## Интерфейс

В существующий `admin/production.html` подключён `production-farm-runtime.js`.

Каждая карточка производственного задания теперь получает дополнительный блок:

- назначенная машина;
- рабочий статус машины;
- тип операции;
- фактическое машинное время;
- плановое машинное время;
- действия «Настроить», «Старт», «Пауза», «Продолжить», «Готово».

Таймер активного запуска обновляется в интерфейсе каждую секунду. В БД сохраняются закрытые сегменты, поэтому перезагрузка страницы или переход между устройствами не теряет учёт времени.

Кнопка **«Машины»** открывает обзор фермы:

- сколько машин свободно / работает / стоит в очереди / недоступно;
- текущее задание каждой машины;
- размер очереди;
- фактическое машинное время за текущий день;
- форма владения.

Realtime подписка обновляет блоки при изменении заданий, запусков или оборудования.

## Проверка на рабочей БД

Миграция применена к рабочей Supabase БД. В транзакционном тесте под ADMIN:

- существующему заданию назначено оборудование;
- автоматически открыт runtime-сегмент;
- после реального ожидания выполнена пауза;
- сегмент закрыт;
- фактическое машинное время увеличилось;
- оборудование перешло из `WORKING` в `QUEUED`;
- после `ROLLBACK` тестовые назначения и runtime-сегменты не сохранились.
