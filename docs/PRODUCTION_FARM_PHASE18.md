# Production Farm — Phase 18: сроки выплат и контроль просрочки

## Цель

Phase 18 переводит выплаты владельцам оборудования из режима «помним вручную» в контролируемый процесс с явной датой обязательства, автоматическим определением просрочки и ежедневными уведомлениями ответственным сотрудникам.

Система **не придумывает юридический срок оплаты**. Дата появляется только:

1. из `settlement_day`, уже зафиксированного в договоре;
2. либо через явное назначение сотрудником с правом управления расчётами/договорами.

## Данные обязательства

В `equipment_owner_settlements` и `equipment_lease_charges` добавлены:

- `payment_due_date` — дата, к которой должна быть выполнена выплата;
- `deadline_source` — `CONTRACT_DAY` или `MANUAL`.

Для новых расчётов trigger пытается вычислить срок только при наличии `equipment_contracts.settlement_day`.

Если договорного дня нет, `payment_due_date` остаётся `NULL`, а интерфейс показывает **«Дата не назначена»**.

## Расчёт договорной даты

`equipment_payment_default_due_date(contract_id, period_end)`:

- берёт только `settlement_day` договора;
- ищет первую допустимую календарную дату строго после окончания расчётного периода;
- если в месяце нет указанного числа (например, 31 февраля), использует последний день месяца;
- не позволяет сроку оказаться раньше `period_end`.

## Ручное назначение

RPC:

`set_equipment_payment_due_date(entity_type, entity_id, due_date)`

Поддерживает:

- `OWNER_SETTLEMENT`;
- `LEASE_CHARGE`.

Защита:

- только `production.settlements.manage` или `equipment.contracts.manage`;
- оплаченное обязательство менять нельзя;
- дата не может быть раньше окончания периода;
- источник становится `MANUAL`;
- изменения исходной финансовой записи продолжают попадать в существующий аудит.

## Состояния срока

Серверные read-model RPC вычисляют состояние без изменения финансового статуса:

- `NO_DUE_DATE` — дата ещё не назначена;
- `UPCOMING` — срок дальше трёх дней;
- `DUE_SOON` — осталось до трёх дней;
- `DUE_TODAY` — срок сегодня;
- `OVERDUE` — дата прошла, запись ещё не `PAID`;
- `PAID` — обязательство оплачено.

Также рассчитывается `days_overdue`.

## Кабинет владельца

RPC:

`get_my_equipment_payment_obligations()`

возвращает только обязательства текущего `current_partner_id()` со статусами `APPROVED`/`PAID`.

В `partner/equipment.html` подключён `equipment-owner-deadlines.js`, который добавляет вкладку **«Сроки выплат»**.

Владелец видит:

- тип выплаты;
- договор;
- период;
- сумму;
- дату платежа;
- текущее состояние срока;
- количество дней просрочки.

Партнёр не может изменить срок.

## Панель HUB

Добавлены:

- `admin/equipment-payment-control.html`;
- `admin/equipment-payment-control.js`;
- пункт **«Контроль выплат»** в общей навигации.

Экран показывает KPI:

- просрочено;
- срок сегодня/в ближайшие 3 дня;
- обязательства без даты;
- число записей по фильтру.

Сотрудник с правом управления может назначить или изменить срок неоплаченного обязательства.

## Автоматические уведомления

Таблица `equipment_payment_deadline_events` фиксирует уже отправленные события и имеет уникальность:

`entity_type + entity_id + due_date + notice_kind`.

Это не позволяет ежедневному процессу спамить одним и тем же уведомлением.

Типы:

- `DUE_SOON`;
- `DUE_TODAY`;
- `OVERDUE`.

Функция:

`emit_equipment_payment_deadline_notifications()`

вызывается `pg_cron` ежедневно:

`equipment-payment-deadlines-daily` → `0 6 * * *`.

Фоновый RPC не выдан ни `anon`, ни `authenticated`; его вызывает серверный cron.

Уведомления получают активные ADMIN и сотрудники с `production.settlements.manage` / `equipment.contracts.manage`.

## Безопасность

- все SECURITY DEFINER функции используют `search_path=''`;
- `anon` EXECUTE отозван;
- partner RPC получает организацию исключительно через `current_partner_id()`;
- staff read/manage RPC повторно проверяют разрешения;
- таблица событий включена в RLS;
- прямые записи в таблицу событий клиентам не выданы;
- финансовые статусы `APPROVED/PAID` не подменяются состоянием просрочки.

## Проверка на рабочей Supabase

Транзакционный тест с `ROLLBACK` подтвердил:

1. договор с `settlement_day=10` автоматически сформировал допустимый `payment_due_date`;
2. сотрудник HUB вручную изменил срок;
3. партнёр увидел только своё обязательство и состояние `DUE_SOON`;
4. срок был переведён в просроченный для теста;
5. первый запуск фоновой функции создал ровно одно событие/уведомление;
6. второй запуск не создал дубль;
7. результат: `phase18_payment_deadlines_ok`;
8. после `ROLLBACK` тестовые данные отсутствуют.

Отдельно проверено, что cron-задача `equipment-payment-deadlines-daily` активна, а `emit_equipment_payment_deadline_notifications()` не имеет EXECUTE для `authenticated` и `anon`.
