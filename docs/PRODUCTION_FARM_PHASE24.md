# Production Farm Phase 24 — сверка состояния при возврате

Phase 24 автоматически сравнивает последний завершённый акт `ACCEPTANCE` с конкретным завершённым актом `RETURN` для того же договора и оборудования.

Цель этапа — зафиксировать объективные различия между состоянием «на входе» и «на возврате». Система **не определяет виновного автоматически**, **не создаёт долг**, **не создаёт начисление**, **не списывает деньги** и **не меняет финансовые расчёты владельца**.

## Состояния сверки

- `NO_BASELINE` — завершённого приёмочного акта нет, сравнение невозможно;
- `NO_DISCREPANCY` — база есть, существенных новых расхождений не найдено;
- `OPEN` — найдено материальное изменение, требуется рассмотрение;
- `RESOLVED` — сотрудник HUB зафиксировал итог рассмотрения.

Одна завершённая `RETURN`-инспекция создаёт не более одной сверки.

## Что сравнивается

`build_equipment_condition_delta()` формирует snapshot сравнения и фиксирует:

- оценку состояния до/после и факт ухудшения;
- работоспособность до/после и факт ухудшения;
- показания наработки до/после и дельту часов;
- изменения пунктов чек-листа;
- новые пункты чек-листа со статусом `ISSUE`;
- дефекты при приёмке;
- дефекты при возврате;
- новые дефекты, которых не было в приёмочном акте.

Рост наработки сам по себе является информацией и **не считается материальным расхождением**. `material_change=true` только при ухудшении общего состояния, ухудшении работоспособности, новом замечании чек-листа или новом дефекте.

## Автоматическое создание

После перехода `RETURN`-осмотра в `COMPLETED` триггер `create_equipment_condition_comparison_after_return()` вызывает внутренний `ensure_equipment_condition_comparison()`.

Создаётся запись `equipment_condition_comparisons` и центральный документ типа `EQ_CONDITION_COMPARISON`. Документ содержит исходный immutable `delta_snapshot` и ссылки на:

- сверку;
- возвратный осмотр;
- приёмочный осмотр, если он существует;
- оборудование;
- договор;
- партнёра;
- процедуру расторжения, если возврат относится к ней.

При `OPEN` ответственным сотрудникам HUB отправляется предупреждение.

## Неизменяемость

После создания нельзя переписать исходные идентификаторы, `delta_snapshot`, признак `material_change` или исходный документ. Удаление сверки запрещено.

После `RESOLVED` запись полностью закрыта от дальнейшего изменения (`RESOLVED_COMPARISON_IMMUTABLE`). Ответы владельца хранятся append-only; update/delete блокируется ошибкой `COMPARISON_RESPONSE_APPEND_ONLY`.

## Ответ владельца

В кабинете владельца вкладка «Сверка возврата» показывает только его собственные сверки через `get_my_equipment_condition_comparisons()`.

Для `OPEN` владелец может:

- `ACKNOWLEDGED` — подтвердить ознакомление и согласие с зафиксированной сверкой;
- `DISPUTED` — заявить возражение с обязательным комментарием.

Повтор одного и того же текущего ответа блокируется. Возражение создаёт предупреждение сотрудникам HUB.

Ответ владельца не меняет исходный акт и не создаёт финансовых последствий.

## Решение HUB

Сотрудник с `equipment.manage` или `equipment.contracts.manage` может закрыть `OPEN`-сверку только с обязательным текстовым обоснованием и одним из кодов:

- `NORMAL_WEAR` — нормальный износ;
- `HUB_RESPONSIBILITY` — ответственность HUB;
- `OWNER_RESPONSIBILITY` — ответственность владельца;
- `SHARED` — совместная ответственность;
- `NO_CLAIM` — требований нет;
- `OTHER` — иное решение.

Это **классификация результата рассмотрения**, а не финансовая операция. Phase 24 не создаёт ни платёж, ни удержание, ни задолженность, ни взаиморасчёт автоматически.

## Интерфейс

HUB: `admin/equipment-condition-comparisons.html` — KPI, поиск, фильтры, детальная сверка «до → после», ответ владельца и ручное решение сотрудника.

Партнёр: модуль `partner/equipment-owner-condition-comparisons.js` добавляет read-only данные сверки и действия подтверждения/возражения для открытого случая.

## Безопасность

Таблицы:

- `equipment_condition_comparisons`;
- `equipment_condition_comparison_responses`.

RLS разрешает владельцу читать только записи своего `current_partner_id()`. Прямые browser mutations запрещены; изменения выполняются через контролируемые RPC. Внутренние builder/creator/trigger/guard функции не выдаются browser roles. SECURITY DEFINER функции используют `set search_path=''`.

## Проверка рабочей Supabase

Полный сценарий проверен в транзакции с `ROLLBACK` и завершился результатом:

`phase24_condition_comparisons_ok`

Тест подтвердил:

- автоматическое создание сверки после `RETURN`;
- обнаружение ухудшения `GOOD → FAIR`;
- обнаружение ухудшения `READY → LIMITED`;
- обнаружение одного нового замечания чек-листа;
- обнаружение одного нового дефекта;
- расчёт дельты наработки `+6 ч`;
- создание документа `EQ_CONDITION_COMPARISON`;
- изоляцию владельцев A/B;
- append-only возражение владельца;
- ручное закрытие сотрудником как `NO_CLAIM`;
- неизменяемость после `RESOLVED`;
- отсутствие автоматических финансовых операций;
- отсутствие тестовых данных после `ROLLBACK`.
