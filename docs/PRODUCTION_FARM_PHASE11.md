# Производственная ферма — этап 11: автоматический контроль производства

## Задача этапа

Этап 10 показывает аналитику. Этап 11 превращает её в постоянный контроль: система сама подсвечивает оборудование, у которого показатели пересекли заданные бизнесом пороги.

Контроль не создаёт второй журнал производства и не меняет производственные факты. Он читает уже канонические источники:

- `production_oee_daily` — время, качество, план/факт и экономика;
- `equipment_capacity_rules` — доступная календарная мощность;
- `equipment_assets` — состояние станка и дата следующего ТО.

## Настройки контроля

Добавлена singleton-таблица `production_monitor_settings`.

Настраиваются:

- глубина анализа: 1–365 дней;
- порог высокой загрузки;
- минимально допустимое качество;
- порог доли простоя;
- минимальная допустимая производственная маржа;
- за сколько дней предупреждать о ТО.

По умолчанию:

- период — 30 дней;
- загрузка — 85%;
- качество — 95%;
- простой — 10%;
- маржа — 0 ₽;
- ТО — предупреждение за 14 дней.

Это не «вечные правильные цифры». Администратор с `production.manage` может менять их через RPC `save_production_monitor_settings(...)` без правки SQL или JavaScript.

Прямые `INSERT/UPDATE/DELETE` роли `authenticated` закрыты. Таблица доступна сотрудникам только на чтение по production-permission, изменения идут через permission-checked `SECURITY DEFINER` RPC.

## Read model `production_equipment_monitor`

`SECURITY INVOKER` view формирует текущую карточку контроля для каждого не списанного станка.

В ней есть:

- фактическое время работы;
- простой;
- количество остановок;
- годный выпуск, брак и переделка;
- плановое и фактическое машинное время;
- выручка и производственная себестоимость;
- доступная мощность за окно анализа;
- загрузка мощности;
- доля простоя;
- first-pass качество;
- производственная маржа;
- дата следующего ТО;
- массив активных сигналов.

## Сигналы

Поддерживаются:

- `SERVICE_OVERDUE` — ТО просрочено;
- `SERVICE_DUE` — ТО приближается;
- `HIGH_UTILIZATION` — загрузка выше заданного порога;
- `LOW_QUALITY` — качество ниже порога;
- `HIGH_DOWNTIME` — доля простоя выше порога;
- `LOW_MARGIN` — маржа ниже допустимого значения;
- `EQUIPMENT_UNAVAILABLE` — оборудование находится в ремонте / обслуживании / неисправности.

Сигнал — это повод проверить ситуацию, а не автоматический диагноз. Например, высокая загрузка может быть отличным результатом, пока она не начинает срывать сроки и создавать очередь.

## Hardening после первого запуска

Первая версия view повторно использовала `production_capacity_between(...)`. Это оказалось плохой композицией: RPC содержит собственную проверку пользовательского permission, поэтому системный SQL/service tooling без пользовательского JWT получал `PERMISSION_DENIED`.

Добавлена отдельная hardening-миграция. `production_equipment_monitor` теперь считает доступную мощность непосредственно из канонического `equipment_capacity_rules` и календарных дат.

То есть источник мощности остался один и тот же, но read-model больше не зависит от auth-контекста другого RPC.

После hardening рабочая БД успешно возвращает монитор:

- `A4-EQ-00001 · Epson L805`;
- окно 30 дней;
- загрузка 0%;
- пока нет данных качества и простоя;
- маржа 0 ₽;
- активных сигналов 0.

Это корректное состояние при отсутствии накопленных производственных фактов.

## Интерфейс

На `admin/production.html` добавлена кнопка **«🚨 Контроль»**.

Окно показывает:

- общее количество сигналов;
- количество критичных станков;
- предупреждения по ТО;
- возможные узкие места;
- карточку каждого станка с загрузкой, качеством, простоем и маржой;
- объяснение каждого активного сигнала и рекомендуемое направление проверки.

Для пользователя с `production.manage` доступна кнопка **«⚙ Пороги»**. Изменения применяются сразу и не требуют redeploy frontend/backend.

На кнопке контроля есть badge с количеством активных сигналов. Данные обновляются через Supabase Realtime при изменении настроек, оборудования, календаря мощности, производственных заданий, run-сегментов и операторских событий.

## Безопасность

- `production_monitor_settings` — RLS включён;
- `anon` доступа не имеет;
- `authenticated` получает только `SELECT` на таблицу настроек;
- запись настроек только через permission-checked RPC;
- `production_equipment_monitor` использует `security_invoker=true`;
- мониторинг не имеет write-path к производственным фактам.
