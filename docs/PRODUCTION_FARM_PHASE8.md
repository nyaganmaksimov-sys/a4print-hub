# Производственная ферма — этап 8

Этап 8 добавляет автоматического диспетчера производства поверх календаря мощности из этапа 7. Главная задача — перестать вручную высчитывать свободный станок и время, при этом не дать автоматике самовольно двигать вручную закреплённые задания.

## Дедлайн отделён от окна станка

Раньше `planned_end` одновременно использовался как срок готовности и как окончание занятого окна оборудования. Для автоматического планирования это две разные сущности.

В `production_jobs` добавлен `deadline_at`.

- `deadline_at` — обещанный срок готовности;
- `planned_start` / `planned_end` — физическое окно станка;
- старые задания без полноценного машинного плана получили дедлайн из `orders.due_at` или старого `planned_end`;
- существующие полные машинные планы помечены как закреплённые и не будут автоматически передвигаться.

Форма производственного задания теперь редактирует дедлайн, тип операции и плановое машинное время, а окно станка оставляет диспетчеру.

## Автоматический подбор станка

RPC `production_find_dispatch_slot(...)` ищет самое раннее свободное окно.

При поиске учитываются:

- статус и эксплуатационное состояние оборудования;
- недельная мощность из `equipment_capacity_rules`;
- начало рабочего окна и часовой пояс;
- длительность задания `planned_machine_minutes`;
- технический зазор между заданиями;
- уже занятые интервалы;
- горизонт планирования;
- тип операции и маршруты оборудования, если они настроены.

Если для типа операции ещё не создан явный маршрут, диспетчер работает в fallback-режиме и рассматривает доступное оборудование. После настройки хотя бы одного маршрута для этого типа кандидаты ограничиваются только указанными станками.

## Автоплан очереди

RPC `auto_dispatch_production_queue(...)` распределяет только незапланированные и незакреплённые задания.

Очередность:

1. ближайший дедлайн;
2. более высокий приоритет;
3. более раннее создание задания.

Для каждого задания выбирается самое раннее доступное окно. Если свободного окна нет, задание остаётся в очереди и получает диагностическую заметку, а остальные задания продолжают планироваться.

RPC `auto_dispatch_production_job(...)` выполняет то же действие для одного задания.

## Ручное закрепление

В `production_jobs` добавлены:

- `dispatch_locked`;
- `dispatch_source`;
- `dispatch_note`;
- `last_dispatched_at`.

Источники плана:

- `AUTO` — автоматический диспетчер;
- `MANUAL` — пользователь вручную поставил окно;
- `FAULT_REPLAN` — автоматический перенос после сбоя оборудования;
- `LEGACY` — существовавший до этапа 8 план.

Закреплённое задание автоматикой не перемещается. Пользователь может разблокировать его в интерфейсе диспетчера.

## Drag & drop календарь

В `admin/production.html` подключён модуль **«🧠 Диспетчер»**.

Он показывает:

- календарь по каждому физическому станку;
- задания внутри дней;
- прогноз опоздания относительно дедлайна;
- задания на недоступном оборудовании;
- нераспределённую очередь;
- источник плана и состояние ручной блокировки.

Задание можно перетащить на нужный станок и день. RPC `schedule_production_job_into_day(...)` сам ищет первое свободное окно внутри мощности выбранного дня. Браузер не вычисляет конфликтующие интервалы самостоятельно — решение остаётся на сервере.

## Автоперенос при поломке

Trigger `trg_replan_production_jobs_after_equipment_fault` реагирует, когда оборудование впервые переходит в одно из недоступных состояний:

- `MAINTENANCE`;
- `REPAIR`;
- `FAULT`;
- `WAITING_PARTS`;
- `OFFLINE`;
- `RETIRED`;
- либо списывается.

Автоматически обрабатываются только незакреплённые задания `NEW`, `QUEUED`, `PAUSED`.

Вручную закреплённые задания не двигаются — это принципиальная защита от неожиданного перепланирования.

Если существует альтернативный свободный станок, задание получает новый слот. Если альтернативы нет, машинный план очищается и в `dispatch_note` записывается причина, чтобы оператор увидел проблему в диспетчере.

`IN_PROGRESS` автоматически не переносится: уже выполняемая работа требует решения человека.

## Настройки диспетчера

Таблица `production_dispatch_settings` хранит:

- IANA-часовой пояс;
- время начала рабочего окна;
- горизонт автопланирования;
- технический зазор между заданиями.

Стартовое значение часового пояса — `Asia/Yekaterinburg`, рабочее окно начинается в 09:00, горизонт — 30 дней, зазор — 10 минут.

Изменение выполняется через permission-checked RPC `save_production_dispatch_settings(...)`.

## Маршруты операций

Таблица `production_equipment_capabilities` связывает `operation_type` задания с конкретными станками.

Настройка выполняется через `save_production_equipment_capabilities(...)`. В интерфейсе диспетчера типы операций вводятся списком для каждого станка.

Примеры:

- `3D_PRINT`;
- `LASER_CUT`;
- `UV_PRINT`;
- `PHOTO_PRINT`.

Названия не зашиты в код и могут соответствовать реальному производственному процессу компании.

## Безопасность от гонок

Автодиспетчер использует advisory-блокировку по заданию, а запись конкретного окна дополнительно защищена блокировкой по `equipment_id` и существующим trigger `validate_production_job_schedule`.

Даже если два оператора одновременно запускают планирование, физическое пересечение двух открытых заданий на одном станке не должно попасть в базу.

## Проверка рабочей базы

Миграция применена к рабочей Supabase.

Транзакционным тестом подтверждено:

- автоматическое задание получает станок и окно;
- `NEW` переходит в `QUEUED`;
- автоматический план остаётся незакреплённым;
- второе задание на тот же день получает другое, непересекающееся окно;
- ручное размещение получает `dispatch_locked=true`;
- при переводе станка в `FAULT` автоматическое задание снимается с неисправного оборудования и пытается перепланироваться;
- при отсутствии альтернативного станка оно остаётся без машинного окна с диагностикой;
- вручную закреплённое задание при сбое не было перемещено;
- вся тестовая запись и изменение статуса оборудования были полностью откатены транзакцией.
