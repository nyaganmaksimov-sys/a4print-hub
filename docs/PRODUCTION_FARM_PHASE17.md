# Production Farm — Phase 17: подтверждения и расхождения владельца

## Цель

Phase 17 закрывает следующий операционный риск после запуска кабинета владельца: партнёр должен иметь возможность не только увидеть опубликованный расчёт или документ, но и официально зафиксировать свою реакцию.

При этом внешний пользователь **не меняет** исходный расчёт, сумму, статус выплаты или юридический документ. Его ответ хранится отдельным append-only событием.

## Что может сделать владелец

Для доступных ему записей владелец может выбрать:

- **Подтвердить** — зафиксировать, что он ознакомился и согласен с записью;
- **Есть расхождение** — открыть спор с обязательным текстовым пояснением.

Ответы поддерживаются для:

- `OWNER_SETTLEMENT` — подтверждённого или оплаченного расчёта доли владельца;
- `LEASE_CHARGE` — подтверждённого или оплаченного арендного начисления;
- `CONTRACT_DOCUMENT` — опубликованного документа договора оборудования.

Повторная запись того же текущего состояния блокируется `RESPONSE_ALREADY_CURRENT`.

## Append-only журнал

Таблица `equipment_partner_responses` не выдаёт партнёру `INSERT/UPDATE/DELETE` напрямую. Все действия проходят через RPC.

Каждая смена ответа создаёт новую строку. Старые подтверждения и споры не переписываются. Это позволяет восстановить хронологию разногласий при сверке.

Поля:

- партнёр;
- партнёрский пользователь;
- тип и UUID исходной сущности;
- `ACKNOWLEDGED` или `DISPUTED`;
- комментарий;
- время события;
- результат рассмотрения сотрудником HUB;
- кто и когда закрыл расхождение.

## Детерминированный порядок событий

Первый транзакционный тест выявил важную особенность PostgreSQL: `now()` остаётся постоянным внутри одной транзакции. Поэтому два последовательных ответа могли получить одинаковый `created_at`, а сортировка только по времени не гарантировала правильное определение последнего события.

Hardening-миграция добавляет `event_sequence bigint generated always as identity` и уникальный индекс. Текущее состояние и история теперь определяются по монотонному `event_sequence`, а `created_at` остаётся человекочитаемым временем аудита.

## Серверные функции

Миграции:

- `database/migrations/20260915_production_farm_partner_responses.sql`;
- `database/migrations/20260915_production_farm_partner_responses_ordering.sql`.

RPC:

- `submit_equipment_partner_response(text, uuid, text, text)`;
- `get_my_equipment_partner_responses()`;
- `list_equipment_partner_disputes(boolean)`;
- `resolve_equipment_partner_dispute(uuid, text)`.

Партнёр никогда не передаёт `partner_id`: сервер получает организацию через `current_partner_id()` и пользователя через `current_partner_user_id()`.

Для спора комментарий обязателен (`DISPUTE_COMMENT_REQUIRED`). При создании спора ответственным сотрудникам HUB отправляется уведомление.

## Рассмотрение со стороны HUB

Добавлена страница:

`admin/equipment-partner-responses.html`

Она доступна из боковой навигации как **«Ответы владельцев»**.

Очередь показывает:

- организацию партнёра;
- пользователя, который заявил расхождение;
- тип исходной записи;
- комментарий;
- дату;
- открытый/рассмотренный статус;
- итоговое решение HUB.

Закрытие расхождения требует обязательной заметки. Эта операция не меняет исходный финансовый расчёт или документ. Если нужна корректировка расчёта, она оформляется отдельным штатным процессом.

## Кабинет партнёра

В `partner/equipment.html` добавляется вкладка **«Подтверждения»** через `partner/equipment-owner-responses.js`.

Она самостоятельно загружает:

- безопасную витрину Phase 16;
- append-only историю ответов владельца.

Для каждого опубликованного расчёта/начисления/документа показывается текущее состояние ответа и кнопки подтверждения или открытия расхождения.

## Безопасность

- таблица включена в RLS;
- партнёр видит только строки своего `current_partner_id()`;
- внутренние сотрудники видят очередь только при разрешениях расчётов/договоров;
- прямые мутации таблицы для `authenticated` не выдаются;
- mutating RPC доступны `authenticated`, но проверяют роль/партнёра внутри;
- `anon` EXECUTE отозван;
- SECURITY DEFINER RPC используют `search_path=''`;
- исходная сущность перед записью ответа повторно проверяется на принадлежность текущему партнёру и допустимый опубликованный статус;
- история изменений таблицы попадает в существующий `audit_log`.

## Транзакционный тест на рабочем контуре

Тест выполнен в одной транзакции с последующим `ROLLBACK`.

Проверено:

1. создан временный подтверждённый расчёт владельца;
2. партнёр зафиксировал `ACKNOWLEDGED`;
3. повторный `ACKNOWLEDGED` заблокирован `RESPONSE_ALREADY_CURRENT`;
4. `DISPUTED` без комментария заблокирован `DISPUTE_COMMENT_REQUIRED`;
5. спор с комментарием успешно записан;
6. история содержит два append-only события;
7. благодаря `event_sequence` последним однозначно является `DISPUTED`;
8. сотрудник HUB закрыл спор с обязательной итоговой заметкой;
9. `resolved_at` заполнен;
10. результат теста: `phase17_response_lifecycle_ok`;
11. после `ROLLBACK` тестовые данные не сохранены.
