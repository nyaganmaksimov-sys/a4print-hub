# Производственная ферма — этап 10: аналитика и OEE

## Цель

Этап 10 превращает накопленный производственный факт из этапов 7–9 в управленческие показатели. Источниками истины остаются существующие сущности HUB:

- `equipment_capacity_rules` — доступная мощность оборудования;
- `production_jobs` — план, дедлайн, итоговая себестоимость и завершённые задания;
- `production_job_runs` — фактическое машинное время;
- `production_job_events` — простой, годный выпуск, брак и переделка;
- `production_equipment_standards` — новый норматив скорости для расчёта Performance/OEE.

Отдельного параллельного журнала производства не создаётся.

## Что добавлено

### Норматив скорости

`production_equipment_standards` хранит норматив для пары `оборудование + операция`:

- `ideal_cycle_seconds_per_unit` — идеальный цикл в секундах на единицу;
- `target_scrap_percent` — целевой процент брака;
- комментарий и флаг активности.

Изменение выполняется только через `save_production_equipment_standard(...)` и требует `production.manage`. Браузеру таблица доступна только на чтение через RLS.

### Аналитика оборудования

`production_equipment_analytics(from, to)` считает по каждому станку:

- доступную мощность;
- запланированное время;
- фактическое машинное время;
- простой;
- свободную мощность и переработку;
- плановую загрузку;
- фактическое использование мощности;
- runtime availability;
- годный выпуск, брак и переделку;
- Quality;
- покрытие фактической работы нормативами;
- Performance;
- OEE;
- число завершённых и просроченных заданий;
- фактическую производственную себестоимость завершённых заданий.

### Honest OEE

OEE не вычисляется из предположений. Формула применяется только если:

1. есть фактическое машинное время;
2. норматив скорости покрывает не менее 99% фактической работы;
3. есть количественный результат производства;
4. известна доступная мощность оборудования.

Тогда:

`OEE = Availability × Performance × Quality`

где:

- `Availability = min(1, run_minutes / available_minutes)`;
- `Performance = min(1, ideal_seconds / standard_run_seconds)`;
- `Quality = good / (good + scrap)`.

Если данных недостаточно, API возвращает `NULL`, а интерфейс показывает `—` и процент покрытия нормативами. Система не подставляет 100% и не рисует красивое значение из воздуха.

### Pareto простоев

`production_downtime_pareto(from, to)` агрегирует фактические паузы по причинам и возвращает длительность, число событий и долю причины в общем простое.

### UI

На `/admin/production.html` появляется кнопка `📊 Аналитика`.

Экран содержит:

- KPI выбранного периода;
- 7 / 30 / 90 дней и произвольный диапазон;
- таблицу оборудования;
- Pareto простоев;
- редактор нормативов скорости для пользователей с `production.manage`.

## Найденный и исправленный дефект

Во время проверки первая версия аналитики показала 44 640 минут плана при мощности 10 080 минут на полностью пустом станке. Причина — поведение PostgreSQL `LEAST/GREATEST` с `NULL` после `LEFT JOIN`: строка без задания могла давать интервал всего запрошенного периода.

Исправление вынесено в отдельную миграцию `20260914_production_farm_analytics_oee_hardening.sql`. Плановое время теперь агрегируется только при `j.id is not null`.

Историческая миграция не переписывалась после применения к рабочей базе.

## Проверка рабочей Supabase

После hardening пустой станок за 30 дней возвращает:

- `planned_minutes = 0`;
- `planned_load_percent = 0`;
- OEE отсутствует, если нет фактического производства и нормативов.

Дополнительно в транзакции с последующим `ROLLBACK` создан синтетический производственный факт:

- доступная мощность: 480 минут;
- план: 240 минут;
- фактическая работа: 240 минут;
- простой: 60 минут;
- выпуск: 360 годных + 40 брака;
- идеальный цикл: 36 секунд/единицу;
- покрытие нормативом: 100%;
- Performance: 100%;
- Quality: 90%;
- OEE: 45%.

После `ROLLBACK` подтверждено: тестовых заданий и событий в рабочей базе нет.

## Безопасность

- новые таблицы защищены RLS;
- прямой write из браузера в нормативы отсутствует;
- сохранение норматива идёт через permission-checked RPC;
- аналитические RPC требуют `production.view`, `production.analytics.view` или `production.manage`;
- диапазон аналитики ограничен 400 днями;
- OEE не строится при неполных исходных данных.
