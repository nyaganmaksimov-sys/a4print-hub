# Production Farm Phase 22 — доказательство согласования и подписи ДС

Phase 22 закрывает разрыв между «сотрудник HUB нажал, что ДС подписано» и фактическим доказательством согласования. Система не называет портальное подтверждение квалифицированной электронной подписью: она фиксирует проверяемое действие владельца, а юридический способ подписания выбирается отдельно.

## Источники подтверждения подписи

Поддерживаются три метода:

- `PORTAL_ACCEPTANCE` — владелец авторизован в партнёрском кабинете и явно подтверждает условия ДС;
- `PAPER` — HUB фиксирует полученный бумажный подписанный экземпляр с обязательным реквизитом;
- `EXTERNAL_ESIGN` — HUB фиксирует идентификатор/реквизит внешней электронной подписи.

Для бумажного и внешнего способа пустой реквизит блокируется ошибкой `SIGNATURE_REFERENCE_REQUIRED`.

## Портальное согласование

Phase 22 переиспользует append-only журнал `equipment_partner_responses` из Phase 17. Тип `CONTRACT_DOCUMENT` теперь принимает документы `EQ_CONTRACT_AMENDMENT`.

Владелец может:

- `ACKNOWLEDGED` — подтвердить, что ознакомился и согласен с условиями;
- `DISPUTED` — зафиксировать расхождение/замечание с обязательным текстом.

Каждое событие хранит `partner_id`, конкретный `partner_user_id`, `event_sequence`, комментарий и время. Для подписи по порталу последним ответом обязательно должен быть `ACKNOWLEDGED`; иначе сервер возвращает `PARTNER_ACCEPTANCE_REQUIRED`.

## Неизменяемое evidence

Таблица `equipment_contract_amendment_signatures` хранит одну запись доказательства на ДС:

- amendment / contract / partner / document;
- способ подписи;
- ссылку на partner response для портального способа;
- внешний реквизит для бумаги/внешней ЭП;
- JSON evidence snapshot;
- сотрудника, зафиксировавшего доказательство;
- точное время.

UPDATE и DELETE блокируются trigger-ом `SIGNATURE_EVIDENCE_IMMUTABLE`. Browser roles имеют только SELECT; запись выполняется только через RPC.

## Защита старого workflow

Старый `mark_equipment_contract_amendment_signed()` оставлен для совместимости, но больше не может подписать документ по одному подтверждению сотрудника. Он вызывает новый evidence workflow с методом `PORTAL_ACCEPTANCE`, поэтому без события владельца возвращается `PARTNER_ACCEPTANCE_REQUIRED`.

Основной RPC: `record_equipment_contract_amendment_signature(amendment_id, method, reference, notes)`.

После успешной фиксации evidence документ переходит `APPROVED → SIGNED`, а `document_status_history` получает запись с методом и реквизитом. Далее Phase 21 применяет условия ДС обычным `apply_equipment_contract_amendment()`.

## Интерфейс

HUB на странице допсоглашений получает:

- `Подпись по порталу` — доступна только после подтверждения владельца;
- `Бумажная подпись` — требует реквизит экземпляра;
- `Внешняя ЭП` — требует внешний идентификатор;
- отображение уже зафиксированного evidence и метода.

В партнёрской вкладке `Допсоглашения` появляется блок `Подписание допсоглашений` с кнопками `Подтверждаю условия` и `Есть замечания`, а также состоянием ответа и зафиксированного способа подписи.

## Проверка на рабочей Supabase

Полный сценарий выполнен внутри транзакции с `ROLLBACK` и завершён результатом:

`phase22_signature_evidence_ok`

Проверено:

- старый sign RPC без ответа владельца блокируется;
- `EQ_CONTRACT_AMENDMENT` принимается механизмом partner responses;
- портальное подтверждение создаёт evidence с точным `partner_response_id`, `partner_user_id` и event sequence;
- документ становится `SIGNED` только после evidence;
- ДС после этого штатно применяется;
- бумажный способ без реквизита блокируется;
- бумажный способ с реквизитом записывается;
- попытка UPDATE evidence блокируется `SIGNATURE_EVIDENCE_IMMUTABLE`;
- тестовые записи после `ROLLBACK` отсутствуют.
