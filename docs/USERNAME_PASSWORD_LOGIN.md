# A4PRINT HUB: вход по логину и паролю

## Что меняется

На страницах входа HUB, кассы (в том числе старой POS-страницы) и мобильного HUB вместо email показывается **Логин**. Пароль остаётся прежним.
Форма стала простой; вход через Google убран с основного экрана. Уже выданные
сессии, PIN-коды кассы и персональные права доступа не меняются.

Supabase Auth всё ещё проверяет пароль, используя внутреннюю привязку логина
к существующей учётной записи. **Это изменение интерфейса и маршрута входа,
а не замена Supabase на собственную авторизацию.** Пока Supabase возвращает
HTTP 402 из-за лимита трафика, вход будет недоступен.

## Как устроено

1. Браузер отправляет логин и пароль только по HTTPS в API
   `POST /api/v1/mobile/auth/password`.
2. API проверяет формат логина, находит идентификатор пользователя в
   `staff_login_aliases` (таблица закрыта для браузера), через служебный
   доступ узнаёт текущий внутренний email и передаёт его с паролем в Supabase Auth.
3. Supabase возвращает сессию; роли и права проверяются как раньше.
4. Старые версии приложений, пока не обновились, могут продолжать отправлять
   email и пароль. Этот запасной режим оставлен для безопасного перехода.

Пароли не сохраняются в таблице логинов. В коде нет универсального пароля
или обхода доступа. Ошибка неверного логина и неверного пароля одинаковая.

## Как назначаются логины

Тестовая миграция `supabase/migrations/20261105102000_staff_login_aliases.sql`
создаёт закрытую таблицу и назначает существующим активным сотрудникам логин
из части email **до знака @**, если такой логин допустим и уникален.

Формат: 3–64 символа, латинские буквы, цифры, точка, дефис и подчёркивание.
Первые символ — буква или цифра; ввод регистронезависимый.
Если логин конфликтует, автоматическое назначение пропускается. Администратор
может назначить нужный логин в тестовой базе и затем в основной:

```sql
-- Замените оба значения собственными; никогда не публикуйте идентификаторы.
insert into public.staff_login_aliases (username, auth_user_id)
values ('operator_01', '<auth-user-uuid>')
on conflict (auth_user_id) do update set username = excluded.username;
```

По соображениям безопасности приложение не имеет открытой функции
«получить email по логину». Новый сотрудник получает логин после создания
учётной записи администратором. Регистрационный email по-прежнему нужен для
служебных задач (уведомления и восстановление доступа), но в форме входа
он не отображается.

## Что проверять перед публикацией

1. Резервная копия базы и списка сотрудников.
2. Применить миграцию на тестовой базе и проверить отсутствие невыданных логинов:
   `select count(*) from public.users u left join public.staff_login_aliases a on a.auth_user_id=u.auth_user_id where u.auth_user_id is not null and u.is_active and a.auth_user_id is null;`
3. Проверить права на таблицу: `anon` и `authenticated` не могут её читать.
4. Проверить корректный / неверный логин, неверный пароль и отказ при отключённом пользователе.
5. Проверить HUB на ПК и телефоне, вход в кассу и отдельно 3D-ARTPRINT (PR #390);
   **PIN-вход сотрудников кассы должен остаться прежним**.
6. Проверить работу старого клиента, который отправляет `email`, до обновления EXE.
7. Проверить CORS и работу без VPN; при `HTTP 402` тест остановить,
   не выдавать ошибку Supabase за неверный пароль.
8. Только после проверки — публикация; нужен план отката.

## Порядок выкладки

1. Резервное копирование. 2. SQL-миграция. 3. API с обратной совместимостью.
4. Проверки обоих вариантов входа. 5. Обновление веб-форм.
6. Обновление настольной кассы через существующий механизм обновлений.

Не запускать обновление страницы раньше миграции и API: новый логин
иначе будет отвергнут. Не применять миграцию в рабочей базе до снятия
ограничений и тестирования сессий.
