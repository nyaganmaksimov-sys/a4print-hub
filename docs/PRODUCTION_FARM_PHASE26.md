# Production Farm Phase 26 — требования по состоянию оборудования

Phase 26 добавляет отдельный управляемый контур требований после того, как Phase 24-сверка состояния уже рассмотрена сотрудником HUB и переведена в `RESOLVED`.

## Принцип

Требование — это формализованная позиция стороны по уже рассмотренному расхождению состояния оборудования. Оно не является бухгалтерской проводкой.

Система **не создаёт долг**, **не создаёт платёж**, не формирует штраф, удержание, арендное начисление или расчёт владельцу автоматически. Сумма, срок, основание и доказательства указываются сотрудником вручную. Финансовое исполнение остаётся отдельным явным действием.

## Когда можно создать требование

Кандидатом может быть только сверка `equipment_condition_comparisons` со статусом `RESOLVED`, если решение не равно:

- `NO_CLAIM` — без требований;
- `NORMAL_WEAR` — нормальный износ.

На одну сверку допускается только одно требование.

Направление требования выводится из уже зафиксированной ответственности:

- `OWNER_RESPONSIBILITY` → `HUB_TO_OWNER`;
- `HUB_RESPONSIBILITY` → `OWNER_TO_HUB`;
- `SHARED` → `MUTUAL`;
- `OTHER` → направление сотрудник обязан выбрать явно.

## Жизненный цикл

Статусы требования:

- `DRAFT` — внутренний черновик, владелец его не видит;
- `ISSUED` — выпущено и опубликовано владельцу;
- `ACKNOWLEDGED` — владелец подтвердил;
- `DISPUTED` — владелец оспорил с обязательным комментарием;
- `SETTLED` — стороны урегулировали вопрос;
- `WAIVED` — требование снято;
- `CANCELLED` — отменено.

После выпуска основные поля требования становятся неизменяемыми. Закрытое требование также неизменяемо. Ответы владельца append-only и упорядочены через `event_sequence`.

## Документ-снимок

При выпуске создаётся документ типа `EQ_CONDITION_CLAIM` в центральном архиве `documents`.

Snapshot содержит:

- сумму, валюту и ручной срок;
- основание и доказательства;
- направление требования;
- решение и delta Phase 24-сверки;
- snapshot договора;
- оборудование и владельца;
- связанную процедуру расторжения, если есть;
- сотрудника и время выпуска;
- `financial_posting_created=false`.

Документ связывается через `document_links` с требованием, сверкой, оборудованием, договором, владельцем и расторжением.

## RPC

Staff:

- `save_equipment_condition_claim(...)` — создать/изменить черновик;
- `issue_equipment_condition_claim(uuid)` — выпустить и зафиксировать документ-снимок;
- `list_equipment_condition_claims(boolean)` — рабочая очередь;
- `list_equipment_condition_claim_candidates()` — рассмотренные сверки, для которых допустимо требование;
- `resolve_equipment_condition_claim(...)` — вручную закрыть как `SETTLED`, `WAIVED` или `CANCELLED`.

Partner:

- `get_my_equipment_condition_claims()` — только собственные опубликованные требования;
- `submit_equipment_condition_claim_response(...)` — `ACKNOWLEDGED` или `DISPUTED`.

## Интерфейс HUB

Добавлена страница `admin/equipment-condition-claims.html` — «Требования по состоянию».

Она позволяет:

- выбрать только допустимую `RESOLVED`-сверку;
- вручную задать сумму, срок, основание и доказательства;
- выпустить immutable-требование;
- увидеть ответ владельца;
- вручную закрыть требование и зафиксировать итоговую сумму/ссылку на документ, если стороны урегулировали вопрос.

Финансовая операция этим экраном не создаётся.

## Кабинет владельца

В `partner/equipment.html` добавлена вкладка «Требования».

Владелец видит только свои требования после выпуска, основание, сумму, срок, доказательства и решение по исходной сверке. Он может:

- подтвердить требование;
- оспорить его с обязательным комментарием.

Подтверждение не является автоматической оплатой.

## Security

- обе таблицы имеют RLS;
- browser role получает только `SELECT`, прямые `INSERT/UPDATE/DELETE` не выдаются;
- partner видит только `partner_id=current_partner_id()` и никогда не видит `DRAFT`;
- все внешние RPC используют `SECURITY DEFINER` и `set search_path=''`;
- anon EXECUTE отозван;
- guard-функции недоступны browser roles;
- core выпущенного/закрытого требования защищён trigger guard;
- ответы владельца append-only (`CONDITION_CLAIM_RESPONSE_APPEND_ONLY`).

## Production test

Проведён полный тест в production-схеме с `BEGIN ... ROLLBACK`:

1. создан временный договор и оборудование владельца A;
2. создана `RESOLVED`-сверка с `OWNER_RESPONSIBILITY`;
3. черновик на 12 500 автоматически получил направление `HUB_TO_OWNER`;
4. требование выпущено, создан документ `EQ_CONDITION_CLAIM` с `financial_posting_created=false`;
5. владелец A увидел своё требование;
6. владелец A оспорил его с комментарием;
7. повторный такой же ответ заблокирован `CLAIM_RESPONSE_ALREADY_CURRENT`;
8. владелец B не увидел чужое требование;
9. HUB вручную закрыл требование как `SETTLED` на 5 000 с явной ссылкой на документ;
10. проверено, что для тестового договора не возникло ни одной записи в `equipment_owner_settlements` и `equipment_lease_charges`;
11. вся транзакция откатилась через `ROLLBACK`.

Результат: `phase26_condition_claim_lifecycle_ok`.
