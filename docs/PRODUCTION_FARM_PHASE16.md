# Production Farm — Phase 16: кабинет владельца оборудования

## Цель

Phase 16 даёт внешнему владельцу оборудования прозрачный read-only кабинет внутри существующего `partner/` портала. Партнёр видит только данные своей организации и не получает прямой доступ к внутренним производственным таблицам HUB.

## Что видит партнёр

- своё оборудование по договорам с HUB;
- инвентарный и серийный номер, модель, место установки и операционный статус;
- договоры и ключевые экономические условия;
- расчёты по доле с выручки;
- арендные начисления и зачёт платежей в выкуп;
- факт и реквизиты выплаты;
- безопасный статус инцидентов/ремонтов;
- процедуру расторжения и реквизиты финальных актов;
- опубликованные документы договора;
- юридический snapshot опубликованного документа с возможностью печати.

Внутренние себестоимости оборудования, производственные задания, данные клиентов, номера заказов, ответственные сотрудники и служебные причины ремонта наружу не выдаются.

## Безопасность

Миграция `database/migrations/20260915_production_farm_partner_owner_cabinet.sql` добавляет два RPC:

- `get_partner_equipment_cabinet()`;
- `get_partner_equipment_document(uuid)`.

Обе функции:

- требуют `auth.uid()`;
- получают организацию только через `current_partner_id()`;
- имеют `SECURITY DEFINER` и `search_path=''`;
- не принимают `partner_id` от клиента;
- не выданы роли `anon`;
- выданы только `authenticated`;
- возвращают заранее отобранный набор полей вместо открытия внутренних таблиц партнёру.

`get_partner_equipment_document` дополнительно требует одновременно:

1. связь документа с текущим партнёром через `document_links`;
2. связь документа с договором того же партнёра;
3. тип документа из набора документов оборудования;
4. опубликованный статус: `APPROVED`, `SIGNED`, `ACTIVE`, `TERMINATED` или `ARCHIVED`.

Черновики и документы `PENDING_APPROVAL` внешнему владельцу не показываются.

## Интерфейс

Добавлены:

- `partner/equipment.html`;
- `partner/equipment-owner.js`;
- `partner/equipment-owner.css`;
- `partner/equipment-entry.js`.

`partner/config.js` подключает entry-модуль на авторизованных страницах. На основном портале появляется кнопка **«⚙ Моё оборудование»**.

В кабинете есть вкладки:

- Оборудование;
- Договоры;
- Начисления и выплаты;
- Ремонты;
- Документы;
- Расторжение.

Документы открываются через отдельный защищённый RPC. Браузерный просмотр строится по неизменяемому snapshot из Phase 15 и имеет режим печати.

## Проверка изоляции

На рабочей Supabase выполнены транзакционные тесты с `ROLLBACK`.

### Данные кабинета

В одной транзакции созданы два временных партнёрских договора и два тестовых станка для двух существующих партнёрских аккаунтов. JWT-контекст последовательно переключён на каждого пользователя.

Проверено:

- партнёр A видит только договор `PH16-A` и оборудование A;
- партнёр B видит только договор `PH16-B` и оборудование B;
- чужие договоры и оборудование не попадают в JSON ответа;
- результат: `phase16_partner_isolation_ok`.

### Документы

В транзакции создан опубликованный тестовый документ партнёра A.

Проверено:

- партнёр A получает документ;
- партнёр B при запросе того же UUID получает `DOCUMENT_NOT_AVAILABLE`;
- результат: `phase16_document_isolation_ok`.

После обоих тестов выполнен `ROLLBACK`, тестовые данные не сохранены.

## Security Advisor

Новые RPC намеренно доступны роли `authenticated`, поэтому общий Supabase lint `authenticated_security_definer_function_executable` их перечисляет. В данном случае это ожидаемая архитектура: `SECURITY DEFINER` нужен как узкий read gateway над внутренними таблицами, а проверка `current_partner_id()` выполняется внутри функции. Анонимный `EXECUTE` явно отозван.

Остальные найденные Advisor предупреждения относятся к ранее существующим таблицам, функциям и настройкам проекта и не были добавлены Phase 16.
