# Производственная ферма — этап 6

Этап 6 добавляет управленческую аналитику по экономике каждого станка без создания отдельной ERP-модели. Расчёты строятся на уже существующих производственных заданиях, фактической себестоимости, журнале обслуживания и расчётах с владельцами.

## Что считает система

Для каждого оборудования доступны:

- выполненные производственные задания;
- фактическое машинное время;
- выручка производственных операций;
- машинная, электрическая и материальная составляющие себестоимости;
- общая производственная себестоимость;
- производственная маржа;
- стоимость обслуживания и ремонтов;
- маржа после сервиса;
- условная загрузка;
- простая окупаемость;
- сигнал «эксплуатировать / проверить замену»;
- задолженность перед владельцем и согласованные арендные начисления к оплате.

## Read models

### `equipment_economics_daily`

Read-only `SECURITY INVOKER` view объединяет по дням:

- завершённые `production_jobs`;
- `production_job_cost_breakdown`;
- `equipment_service_log`;
- параметры стоимости и замены из `equipment_assets`.

В представлении отдельно сохраняются `operation_revenue`, `production_cost`, `service_cost`, `production_margin` и `net_margin_after_service`. Благодаря этому интерфейс может строить периоды 30 / 90 / 365 дней или всё время без повторной интерпретации производственных данных.

### `equipment_owner_obligations`

Read-only `SECURITY INVOKER` view собирает обязательства по оборудованию:

- согласованную и выплаченную долю владельца по `REVENUE_SHARE`;
- невыплаченный остаток по согласованным расчётам;
- согласованные, но ещё не оплаченные арендные начисления `LEASE` / `LEASE_BUYOUT`;
- общую текущую сумму к оплате.

Арендное начисление существует на уровне договора, поэтому при нескольких станках оно не копируется целиком на каждый станок. Сумма распределяется между оборудованием, которое действовало в период начисления, по `equipment_contract_assets.allocation_weight`. Если все веса нулевые, применяется равное распределение. Это не позволяет итоговой задолженности умножаться на количество единиц оборудования в договоре.

Оба представления закрыты для `anon`; `authenticated` получает только `SELECT`. Поскольку используется `security_invoker`, политики исходных таблиц продолжают действовать.

## Загрузка

До появления отдельного производственного календаря система не выдаёт условную оценку за абсолютную паспортную загрузку.

В интерфейсе показатель явно называется условным и считается так:

`фактические машинные минуты / (8 часов × количество рабочих дней выбранного периода)`.

Для режима «всё время» процент загрузки не показывается, чтобы не создавать ложную точность.

## Окупаемость

Простая окупаемость считается как:

`накопленная маржа после сервиса / база стоимости оборудования`.

База стоимости:

1. `market_value`, если указана;
2. иначе `analogue_purchase_price`;
3. если обе суммы отсутствуют — окупаемость не рассчитывается.

Это управленческий показатель, а не бухгалтерская амортизация.

## Ремонт или замена

Для каждого станка сравниваются расходы на обслуживание за последние 365 дней с заданным порогом:

`analogue_purchase_price × buy_replacement_warning_percent / 100`.

Если годовой сервис достиг или превысил порог, интерфейс показывает **«Проверить замену»**. Если цена аналога или порог не настроены, система честно показывает, что данных для решения недостаточно.

## Интерфейс

В `admin/equipment.html` добавлен блок **«📊 Экономика производственной фермы»**.

Он содержит:

- общую выручку за период;
- производственную себестоимость и сервис;
- маржу после сервиса и её процент;
- машинные часы;
- текущую сумму к выплате владельцам;
- таблицу по каждому станку с загрузкой, окупаемостью, ремонтом/заменой и обязательствами.

Интерфейс адаптирован для мобильного экрана и автоматически обновляется при изменении производственных заданий, оборудования, обслуживания, расчётов с владельцами и арендных начислений.

## Проверка рабочей БД

Обе миграции применены к рабочей Supabase. Представления созданы успешно и проверены также под ролью `authenticated` с действующим ADMIN: RLS/ACL не блокируют штатное чтение интерфейсом.

На момент проверки в реестре есть одно оборудование; в аналитическом представлении есть одна дневная запись, а текущие суммы выручки, производственной себестоимости и обязательств равны нулю — это соответствует имеющимся рабочим данным и не требует искусственного заполнения истории.
